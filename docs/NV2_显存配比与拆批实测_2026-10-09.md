# NV2 显存配比与拆批实测（2026-10-09）

## 结论

本机正式三数据集实验采用 **vLLM `gpu-memory-utilization=0.51`，NV2 embedding batch=4，禁止 OOM 后拆批**。0.53 可以通过当前压力测试，但结束后的显存余量仅约 0.50 GiB；0.51 同样通过，余量约 1.49 GiB，因此选用后者。

这是当前模型、输入上限与单卡并存条件下的实测选择，不代表任意工作负载的全局最优比例。

## 拆批是否改变结果

此前的拆批针对 NV2 向量编码：4 条文本遇到 OOM 后改为两个 2 条批次。它没有拆分 NER 或三元组的 LLM 请求，也没有改写抽取提示词或拆开原始段落。

每条文本独立编码，但 NV2 按批内最长文本进行右侧 padding。改变 batch 形状和 padding 长度会改变部分 FP16 计算的执行路径，因此不能承诺向量逐位一致。

对同样四条真实 HotpotQA 长段落实测，batch4 与两个 batch2 的对比为：

| 项目 | 实测值 |
|---|---:|
| 最低逐条余弦相似度 | 0.9999991655 |
| 最大向量元素绝对差 | 0.0001026988 |
| 平均元素绝对差 | 0.0000136592 |
| 是否逐位相同 | 否 |
| batch4 本进程 PyTorch allocated 峰值 | 19.79 GiB |
| batch2 最大 allocated 峰值 | 17.21 GiB |
| 本组样本 allocated 峰值减少 | 2.58 GiB |

上述数值表明此次差异很小，但未证明全语料召回率完全不变。接近阈值的向量近邻、图边或排序仍可能受影响。为保持本轮实验执行方式一致，正式工作流设置 `PATHCONDRAG_NVEMBED_OOM_SPLIT=false`，五种方法均使用该策略。

allocated 峰值仅统计 NV2 所在进程。reserved 和整卡 free 会包含历史分配缓存以及独立 vLLM 进程，不能直接用它们计算 batch2 节省多少。首次前向还产生约 8.125 MiB 持久工作区，因此冷、热前向增量不应当作同一基线的精确比较。

## 最长输入与压力测试

扫描 `/root/datasets` 中三个完整 corpus，使用正式 NV2 tokenizer 和正式文本格式 `title + 换行 + text`。

| 数据集 | 最长原始输入 tokens | 超过既有 2048 上限的段落数 |
|---|---:|---:|
| HotpotQA | 2152 | 1 |
| 2WikiMultiHopQA | 1810 | 0 |
| MuSiQue | 883 | 0 |

HotpotQA 最长段落为 `Nashville Terminal Subdivision`。它仍按正式流程原有的 2048 上限编码；本轮没有进一步缩短输入上限。

测试包含各数据集最长四条真实文本、最长文本重复四条、四条均达到 2048 的边界输入、带原查询指令的边界输入、实体与事实输入，共 13 次完整 batch4 前向。人工重复段落只用于压力测试，不写入正式索引。

| vLLM 显存比例 | 完整 batch4 压力测试 | 与 NV2 重叠的八路 API 请求 | 压测后整卡余量 |
|---|---|---|---:|
| 0.55 | 首个最长批次 OOM | 未执行 | 不适用 |
| 0.53 | 13 次全部通过 | 全部 200，3 次 NV 前向确实重叠 | 约 0.50 GiB |
| 0.51 | 13 次全部通过 | 全部 200，3 次 NV 前向确实重叠 | 约 1.49 GiB |

0.55 的错误发生在申请下一块 512 MiB 时，当时可用约 512 MiB；这个错误只描述失败当下的下一次申请，不能当作整个前向总共只缺多少显存的精确结论。

API 每条请求有 5700 输入 tokens，`max_tokens=2048`、温度 0、`enable_thinking=false`，实际返回短 JSON。它验证八路长输入请求与 NV2 同卡重叠可用，并未测试八条都生成满 2048 tokens。0.51 服务的 KV 容量为 51,472 tokens；八条都接近 8192 的请求需要由 vLLM 调度排队或抢占，客户端并发 8 不意味着八条最大上下文必须同时驻留。

两次成功测试均确认 NV2 参数为 `torch.float16`，全部模型位于 `cuda:0`。没有量化、CPU offload 或降低精度。

## 正式运行与复现

保持 vLLM 所用模型、BF16、`max-model-len=8192` 和启动参数，仅改变显存比例。PathCondRAG 使用 `rag` 环境，API 服务使用 `vllm` 环境。检索与索引 LLM 并发均为 8；检索、三元组输出上限仍为 2048，NER 沿用原来的 512，thinking 关闭。

正式脚本：`scripts/run_multi_dataset_retrieval_nv2.sh`。先构建三套共享索引，再运行三数据集各五种方法，共 15 组检索，保留详细 Top10，不运行 QA。

结果根目录：`outputs/3multi_hop_datasets_results_with_nv2_10_8`。实测 fixture、三份 probe、选择依据以及服务原始命令集中保存在该目录的 `metadata/nv2_memory_tuning/`。停止时尚未保存向量或图，已清理未完成的索引目录，正式重建不复用此前拆批产生的向量。

```bash
tail -f /root/PathCondRAG/outputs/3multi_hop_datasets_results_with_nv2_10_8/logs/run_nv2.log
```

需要重测时，先停止正式 NV2 作业，再使用诊断入口；不要与正式 embedding 进程同时加载另一份 NV2：

```bash
/root/anaconda3/envs/rag/bin/python -B scripts/nvembed_memory_probe.py \
  --fixtures outputs/3multi_hop_datasets_results_with_nv2_10_8/metadata/nv2_memory_tuning/longest_input_fixtures.json \
  --report /tmp/nv2_memory_recheck.json \
  --utilization 0.51 --llm-base-url http://127.0.0.1:8035/v1
```
