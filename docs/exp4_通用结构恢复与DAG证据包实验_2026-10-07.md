# exp4：通用结构恢复与 DAG 证据包实验

## 1. 本轮目标与对照

上一轮 `bridge_support` 的三种新增配置在每个数据集 60 题的配对筛选中均没有改变实际排名。有限关系模板和仅在原 Top10 内交换的策略，没有形成新的收益。本轮扩大可处理的结构范围，用当前 `plan_prune` 作为重新运行的同题对照，保留已有的 2Wiki 改善，检查 HotpotQA 是否有新增收益及 MuSiQue 是否保持稳定。

| 配置 | 开关 | 需要回答的问题 |
|---|---|---|
| baseline | planning,plan_prune | 当前算法在本轮样本上的表现 |
| dag_package（A） | baseline + dag_package | 相同规划、绑定和候选下，成组选择是否有效 |
| structural_recovery（B） | baseline + structural_recovery | 修复结构失败是否带来新证据 |
| structural_package（A+B） | baseline + 两者 | 修复输出固定之后，选择是否仍有增量 |

旧模块 `package`、`bridge_recovery` 不自动加入本轮。新模块均是独立开关，关闭时委托原实现；不修改公共索引和 `/root/baseline/HippoRAG` 原始源码。

## 2. B：按结构失败触发的恢复

文件：`src/pathcondrag/evidence_structural_recovery.py`。

原规划和依赖检索先正常执行。只有以下在线诊断触发恢复：

1. 两次原规划之后仍为空，或显式依赖引用无效。
2. 后继节点需要的中间节点没有成功绑定。
3. 未绑定的根节点仍包含“某作品的作者”“某机构的负责人”等嵌套未知实体描述。

已完整绑定的 DAG、单纯末端属性没有找到证据且没有结构异常的情况，保持原流程。这里按问题和在线诊断触发，不读取数据集名称、gold、答案或分解标签。

每题最多新增一次修复规划请求。提示词要求恢复最内层未知实体，使用 `r1` 等 ID 和 `${r1.answer}` 字面引用，保留输入实体、年份、角色、位置、关系方向和最终属性。静态子问题仅作为结构参考，不作为事实。节点最多 6 个，依赖深度最多 4；比较结果等可由已取回值计算的节点不用于检索。

修复需要通过依赖校验、输入数字/名称/部分限定词保留检查及已有关系一致性检查。重复原规划、引入输入中没有的实体、丢失明确条件，均拒绝。词面检查只能筛掉明确错误，不能证明任意规划语义都正确。

修复节点使用原依赖检索和引用核验。完全相同的问题、答案类型和核验文档可以复用本窗口的核验结果；不同输入仍正常调用 LLM。**一次规划之外可能新增多次节点核验，不能说“总共只增加一次请求”。** 整题共享检索次数上限 20，保留并发 8；embedding 仍在原调用线程执行。

只有修复 DAG 所有节点均有实际文档中的有效引用、并与最终 winning bindings 一致，才替换原 DAG。修复失败保留原候选和绑定，记录真实消耗及失败诊断。这个回退避免不完整修复直接替换原结果，但不能保证成功修复后的指标一定不退化。

## 3. A：一般 DAG 的祖先闭合证据包选择

文件：`src/pathcondrag/evidence_dag_package.py`。

### 3.1 证据资格

原选择流程完成后，再考虑已有候选池中、原 Top200 内的文档。要求对应同一 winning branch 的绑定，引用是源文连续子串，答案与实体身份一致，依赖要求满足，且有明确局部关系支持。LLM 置信度达到阈值只是必要条件之一。

当前关系检查仍是有限源文语法，涵盖部分创作者、出生/死亡属性、地理归属、改编、创办等关系；未知关系、任意比较 join 和一般语义蕴含不凭高置信度晋级。跨句指代或名字别名只在标题/紧邻身份能支持时使用。保留这些边界，避免通过放宽核验制造表面提升。

### 3.2 有限联合选择

对最多 6 节点、深度 4 的 DAG 枚举祖先闭合节点子集（最多 64 个）；每节点最多保留 3 个已核验文档。共享文档只占一个位置，支持串行链、平行比较分支及较长链。

在固定文档预算下，候选排序依次最大化：

1. 已闭合的完整终端分支数。
2. 带齐祖先支撑的节点覆盖数。
3. 更少的新文档换入。
4. 更靠前的原始排名。

只有相对原前缀有严格结构覆盖改善才应用。先优化 Top5，再将优化后的 Top5 固定在 Top10 内继续选择。原第 1、2 名固定，原前缀中的可信证明受保护；没有容量或明确增益时保留原排名。

本轮允许原第 11～200 名的有支撑文档进入 Top10，拓宽了上一轮只能在 Top10 内交换的范围。保持同一连续排序、Top200 集合和文档唯一性；没有额外 LLM 请求和额外检索。固定前 2 不能保护 R@5、R@10 不退化，因为现有相关文档可能被替换，仍需配对评估。

## 4. 分离组件贡献

A 必须复用本阶段 baseline 的私有缓存；A+B 必须复用本阶段 B 的已完成私有缓存。脚本逐题核对规划、绑定、分支、路由、规划/核验输出和调用计数一致，同时要求 A 与 A+B 没有新的 HTTP 请求。这样分别报告：

- A − baseline：选择机制的独立贡献。
- B − baseline：结构恢复的独立贡献。
- A+B − B：在修复证据上的选择增量。
- A+B − A：组合中的恢复增量。

如果组合进入确认阶段，先运行 B 再运行 A+B，B 可以只是必要父对照。只有组合超过 baseline 不能证明两个组件都有效；等效收益优先考虑新增模块较少的配置。不同缓存预热历史的耗时不作为效率优越性的证据。

## 5. 样本、预算与筛选标准

### 5.1 实际组数

- 集成测试：三数据集各 2 题，baseline、baseline_replay、A+B 共 **9 组**。
- 配对筛选：三数据集各 **60 题**，四种配置共 **12 组**。
- 若有符合条件的新增 HotpotQA 信号：独立 **30 题/数据集**，最多两个候选或必要父对照，新增 **6 或 9 组**；没有信号则跳过。
- 合计 **21～30 组**，本轮不会自动运行全量或 QA。

固定集成样例为 HotpotQA `[197,572]`、2Wiki `[75,584]`、MuSiQue `[93,567]`；MuSiQue 两题实际 benchmark 跳数为 3 和 4。固定样例只验证流程，排除在筛选和确认之外。CPU 历史回放中个别题的排名改变也不作为本轮新样本增益。

筛选 seed=942、确认 seed=1042。排除既有开发轮次及 `structure_representative`、`failure_focused`、`bridge_support` 的已计划题目。按主要问题结构及跳数分层，保存覆盖报告，不根据检索正确与否选题。原始均值和按主分层全体比例校准的均值都报告；几十题覆盖不足及方差较大仍不可避免。既有本地评估文件已经反复用于开发，本轮不是未接触的最终测试集。

### 5.2 判断标准

原始与校准两个口径下，每个数据集的 **R@1/2/5/10/20/200 都不得相对同题 baseline 下降超过 0.01**。HotpotQA 至少一个 R@5/R@10 指标在两个口径下都上升，才进入探索性确认；不能重复计算 2Wiki 既有 plan_prune 收益。

用户要求的 +0.04 目标继续独立记录，微小正向信号不算达标。HotpotQA 当前全量 R@10=0.9675，绝对上升空间只有 0.0325，这一项本身不可能增加 0.04。确认通过仍需要全量与后续独立评估支持，不能保证论文效果。

### 5.3 固定运行条件

复用 `outputs/3multi_hop_datasets_results_10_5/shared_indexes`；Qwen3-Embedding-8B，embedding batch=4，LLM 并发=8，索引并发配置=8，但本轮不构建索引。max_new_tokens=2048、thinking=false，沿用现有 vLLM 服务。MuSiQue 按授权读取逐题 benchmark 跳数，其余数据集沿用 benchmark 规则；采样与 gold 仅用于离线评估。
