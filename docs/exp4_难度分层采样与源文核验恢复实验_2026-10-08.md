# exp4：难度分层采样、源文核验与失败恢复实验

## 1. 本轮目的

上一轮通用结构实验中，旧 DAG 证据包只在 2Wiki 的少量问题上改善 Top5；结构恢复没有成功应用。HotpotQA 小样本的原对照 R@5 已达 0.9833，难度明显低于全量，无法有效验证新的提升。因此本轮同时修正采样和两个实际瓶颈：

- 源文核验只认识很少的关系，许多已有引用无法形成可信证据链。
- 结构修复依赖模型手写 `${node.answer}`，以及过于字面的词法检查，导致正确依赖或实体也被拒绝。

本轮是开发筛选实验，结果尚不能当作独立测试集结果，也不预先承诺性能提升。

## 2. 五组配置和归因

| 配置 | 在当前 plan_prune 上增加什么 | 对照用途 |
|---|---|---|
| `baseline` | 无 | 当前 plan_prune 的新鲜对照 |
| `dag_control` | 旧 `dag_package` | 保留旧模块，避免重复计算其收益 |
| `source_witness` | 旧 DAG + 源文核验 | 测试引用、实体归属、关系方向检查 |
| `failure_recovery` | 旧 DAG + 失败分类恢复 | 测试结构化依赖修复 |
| `witness_recovery` | 旧 DAG + 上述两项 | 测试组合及相互作用 |

新模块是否有效主要看相对 `dag_control` 的配对变化；同时相对 `baseline` 检查退化。组合分别与两个单模块比较。只有旧 DAG 提升时，报告为旧模块有效，不写成新模块贡献。

### 源文核验

1. 原始引用完全匹配时，直接使用实际 chunk 文本。
2. 引用只改变空白或标点时，允许恢复到原文中唯一的连续字符区间；不接受改写、拼接或省略号代替缺失文字。
3. 根据同篇文档中的显式名称、别名或有明确先行实体的邻近指代，检查主语、谓语、答案及限定条件。出生/死亡、创作者等原有有限关系规则继续使用，增加有限的主动/被动关系框架。
4. 区分 `supported`、`unknown`、`contradicted`。规则不覆盖的情况不当成已验证关系；原先已接受的未知答案保持，明确矛盾才剔除。新的引用恢复和 DAG 证据链必须有支持。

这一步本身不新增 LLM 核验调用；恢复了桥接答案后，后续依赖节点可能增加真实检索和核验调用，因此不宣称整条流程零新增 HTTP。

### 失败分类恢复

先执行原来的依赖检索并保存实际父阶段输出，再区分：依赖结构无效、变量类型冲突、多个人名被绑成一个变量、限定分支没有连接到终点、明确的关系冲突、未解开的复合实体等。有效的原子 DAG 只有引用失败时，不反复重规划。

修复规划改用：

```json
{"nodes":[
  {"id":"r1","question_template":"Who wrote Work X?","inputs":{},"answer_type":"person"},
  {"id":"r2","question_template":"Where was {{person}} born?","inputs":{"person":"r1"},"answer_type":"place"}
]}
```

由代码把 `{{person}}` 渲染为 `${r1.answer}`。槽位必须与输入一一对应，不能只声明依赖，也不能附加无关的“regarding X”。保留问题中的实体、年份、方向、角色和终点属性。最多一次修复规划；最多 6 节点、深度 4，整题仍受 20 次搜索上限约束。

修复只有在任务结构完整、引用字面存在、关系有源文支撑时应用。失败保留原排序输入，并记录实际新增规划/核验/搜索开销；不拿高置信度或“变量都绑定了”替代正确性检查。单人拆分只在修复阶段使用原文中已有的人名，不扩大既有 beam。

## 3. 采样方案

每个数据集固定抽 **90 条筛选、45 条确认**，两阶段互不重叠；历史开发批次和本轮机制测试用例也排除。筛选 seed=1142，确认 seed=1242。

先从已经冻结的全量 `exp4_dependency_binding_plan_prune` 导出逐题历史难度：

| 难度 | 定义 |
|---|---|
| `complete5` | Top5 已包含全部金证据 |
| `missing5_complete10` | Top5 缺证据，但 Top10 完整 |
| `missing10_complete200` | Top10 不完整，但 Top200 完整 |
| `missing200` | Top200 仍不完整 |

将难度与原问题结构分层交叉。稀少层在抽样前按固定规则合并相邻难度，保留问题结构；每个有效层在筛选和确认都至少有一条。层内严格随机抽取，不根据新模块的输赢或运行结果选题，不用贪心挑选“代表题”。保存合并过程、配额、实际难度分布、选中索引、文件哈希和每题入选概率。

检索器只得到索引对应的问题和已授权 hop。历史分数、gold 数量、数据集类型标签和分解结构仅用于离线采样/评估，不输入算法。MuSiQue 仍使用用户指定的逐题 benchmark hop，其余两个数据集保留既有 hop 来源。

同时报告：

- 原始样本均值。
- 按“结构 × 历史难度”层权重还原到**排除历史批次后的初始可用池**的均值，用于筛选和确认。
- 全 1000 条的结构难度校准值，仅作描述诊断；排除题的入选概率为 0，这个值不能消除历史调参，也不是独立测试。

分层覆盖不保证每个语义现象都被几十条覆盖；历史难度也不等于新模型的难度。最终贡献仍需全量验证和另一独立开发/测试划分。

## 4. 缓存、公平性和筛选门槛

所有组复用同一个数据集公共图/向量索引，算法只使用私有索引副本和私有缓存。公共资产前后 SHA256 保持一致。

- 同一阶段先跑新鲜 `baseline`，旧 DAG、A、B 从它的缓存快照出发。
- AB 从已完成 A 的缓存快照出发，确保其修复前父阶段实际输出与 A 一致。
- B 逐题保存并核对修复前的九项实际父输出；AB 同样与 A 核对。
- 旧 DAG 只改选择阶段，因此还必须满足原规划、绑定、路由、模型输出完全一致且新增 HTTP=0。
- 不把 A 改变后续输入造成的调用差异强行归零；各组记录真实 HTTP、缓存与恢复开销。

六项 Recall@1/2/5/10/20/200 都参与防退化：**原始均值和可用池校准均值均不得下降超过 0.01**。有同一 R@5 或 R@10 在两种估计下都改善，才作为探索性候选；另行报告是否达到原定 +0.04 目标，不将微小正向波动写成达标。

筛选后最多确认两个新配置；若组合入选，A 必须作为它的父阶段对照。同一“数据集/指标”在筛选与确认都正向，才记为收益复现。只旧 DAG 有信号时可确认旧 DAG，但标记为已有机制。没有通过防退化的信号则停止，不自动全量。

HotpotQA 当前全量 R@10=0.9675，最大绝对提升为 0.0325；2Wiki 当前为 0.97775，最大提升为 0.02225。+0.04 在这两项上数学上不可达，仍分别保留原目标判定和实际改善记录。

## 5. 运行、保存与读取

正式入口：`scripts/run_exp4_grounded_trials.sh`，实现位于 `scripts/utils/exp4_grounded_trials.py`。

先用同一入口 `--mode smoke` 完成三数据集各两条的对照、缓存重放与组合机制验证，共 9 组。之后 `--mode all` 验证并复用已完成结果，运行 15 组筛选；确认按结果增加 0、6、9 或 12 组。总量 **24～36 组**。每组独立执行，LLM 并发 8、embedding batch=4、max_new_tokens=2048、thinking 关闭，检索输出 Top10 和完整 Top200 候选，QA 不执行。

输出保存在 `outputs/3multi_hop_datasets_results_10_5/`：

- `metadata/exp4_grounded_selection/selection.json`：配置、固定协议、组数、汇总与选择状态。
- `metadata/exp4_grounded_selection/sampling/*.json`：分层配额、历史难度、抽样与权重审计。
- `_exp4_grounded_trials/{smoke,screen,confirmation}/数据集/配置/`：逐题结果、报告、验证凭据和日志。
- `logs/launcher_grounded_difficulty.log`：总进度；每组 `run.log` 保存详细检索日志。

已完成的私有索引副本在验证后清理，结果和验证凭据保留；公共索引与旧实验不删除。缓存快照用于同阶段公平对照及断点验证。

跟踪命令：

```bash
tail -f /root/PathCondRAG/outputs/3multi_hop_datasets_results_10_5/logs/launcher_grounded_difficulty.log
```

## 6. 验证记录

CPU 检查已完成：342 项证据检索模块检查、20 项采样检查、13 项实验协议检查通过。包含实际 MRO 下的健康链无额外请求、程序插值修复与真实父输出快照一致、原始引用恢复、错误方向/年份/所有权反例以及 flags-off 原实现等价。原生 HippoRAG 源码哈希纳入冻结协议，跨阶段也校验。

真实采样审计：三个数据集各有 424 条未进入已排除开发批次的可用题；HotpotQA/2Wiki/MuSiQue 分别形成 6/10/18 个交叉层，原始四种难度均覆盖。90 条筛选样本对应的历史 plan_prune R@5/R@10 为：HotpotQA 0.911111/0.955556，2Wiki 0.938889/0.983333，MuSiQue 0.735185/0.831481。这些是历史基线审计值，新模块的效果尚待实际运行。

2026-10-08 完成同一正式脚本的 9 组实际检查：每个数据集 2 条问题，分别运行 baseline、缓存重放和组合配置。全部输出已验证，基线重放的排名/分数精确一致，公共索引和原生 Hippo 源码一致；共 16 次实际 HTTP，全部 200，重试和失败均为 0。MuSiQue 两个机制用例的 hop 为 2/3；筛选中的 hop 分层另包含 4 跳题，不把所有题固定成 2。

首次启动发现新采样目录未自动创建，在进入实际检索前已修正，并补充正式入口的新目录初始化测试；总日志保留这次初始化错误记录。这与 API/LLM 请求错误不同。

两条 2Wiki 的组合 R@5 从 0.75 到 1.0，属于已经知道的旧 DAG 机制用例，不能算作新模块的平均收益。HotpotQA/MuSiQue 的三个结构触发用例均保守回退，尚未证明新的恢复模块有效；其中一次计划通过结构检查但缺完整源文支持，两次计划仍有任务限定/槽位错误。这些诊断会和筛选中实际触发率、应用率一起报告，不能用“流程跑通”替代效果证据。

后台 `--mode all` 将复核并复用这 9 组，再执行 15 组 90 条筛选以及按信号决定的确认。小样本机制检查只用于排查实现问题，不证明全量检索提升；本轮不会自动运行全量或 QA。
